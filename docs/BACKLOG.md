# 借鉴清单（来自 QQ-agent 调研）

调研对象：GitHub 上的一个成熟 QQ 机器人桌面应用（360 stars、MIT、JavaScript/Electron）。
它是**非官方协议**（OneBot v11 + NapCat，自带 QQ 客户端），我们是**无头服务器 + QQ 官方 API**，
所以只借机制、不抄代码，也不照搬它的交付形态。

每条都标了状态。`✅` 已做、`⏳` 待做、`✗` 明确不做（附理由）。

---

## ✅ 已完成

### 第 1 批：记忆分区加固（`e004bee`）

- ✅ **在场过滤**：群聊里只想起"在场的人"的事（说话的这位 + 搭档 + 这条消息里点到的名字）。
  私聊不设这道闸门。专治"把 A 的事说给 B 听"。
- ✅ **合并幻觉闸门**：合并后断言"条数不得变多"，真变多就整表回滚。
- ✅ **合并前快照**：`data/snapshots/`（留最近 5 份），`restore_memories()` 一键回到拍照那一刻。
  之前 `mark_merged` 不可逆，模型判错就是真的忘掉一件事。
- ✅ **备注名**：`member_notes`（openid → 你给的名字）覆盖平台昵称，归属仍按 openid。
- ✅ **撤回不进模型**：`messages.mid` + `recalled`；撤回后工作记忆/群聊记录/记忆整理三条路都不带它。
  ⚠ 官方文档里没找到撤回事件的正式名字，适配器按名字宽松匹配（含 `RECALL`），平台真推了就用得上。

### 第 2 批：触发聚批 + 发送管道（`ebe91dc`）

- ✅ **触发聚批**：被触发后等 `wake_delay_seconds`（默认 2s）把这段时间的话一起处理。
  三条关键语义：到点才回 / 窗口内追加的消息**并入同一批（没 @ 也算）** / **倒计时不重置**。
  后者很重要——滑动窗口在热闹的群里会让她永远等下去。
- ✅ **响应档位滑条** `response_tier = 0~100`（`giftia/trigger.py`，纯函数）：
  0~19 只应 @、20~44 加关键词、45~69 按概率插线 `(pos-20)/70`、70+ 都可能接。
- ✅ **没命中 = 零 token**：当场标已读（只旁听），不建会话、不调模型。
- ✅ **发送管道**：每会话限频（分/时）+ 分段随机间隔 + 同文 8 秒去重，
  而且**去重只在发送成功后才记账**（提前记账会把合法重试误判成重复、静默丢消息）。
- ✅ **拍一拍**识别（官方文档里没找到正式字段名，按内容宽松识别）。
- ✅ **活跃成员表** `people_stats`（openid → 说过几句 / 最后说话时间）。

### 第 3 批：每人一份档案 + 手动管理（`6a69155`）

- ✅ **每人一份档案**：不另立表——记忆按 `about` 分组就是档案。
  `impressions_block()` 注入紧凑的【你对他们的印象】，**每人 ≤3 条、最多 15 人**。
- ✅ **"还不了解他"**：没形成印象的人会明说，比让她硬编强。
- ✅ **`/profile [名字]`** 看档案、**`/impress 名字 话`** 手动补一条、
  **`/forget 编号`** 让她忘掉记错的（打标记，数据仍在）、**`/reconcile`** 手动整理。
  CLI 与 QQ 都有；QQ 里的 `/reconcile` 先把话说出去再干活，免得她卡着不回。
- ✅ 档案页用**搭档视角**（你看她的记忆），不是在群里当众念。

### 3.7 她自己记一笔：记忆工具（`giftia/agent_tools.py` + 工具循环）

- ✅ **三个工具**：`remember`（当场记一笔）/ `search`（想一下，别硬编）/ `forget`（放掉某条）。
  LLM 层加了 `chat_with_tools` + `ChatReply`/`ToolCall`；DeepSeek 的 function calling
  **真机验证过**——第一轮她就主动调了 `remember` 记下"他叫椎名"。
- ✅ **最后一轮不给工具**：光在提示词里催"快说话"是不够的，她可能又去调工具，
  用户就永远等不到回复。拿掉工具才是真正的保证（`tools_max_rounds`，默认 3）。
- ✅ **可用性只有一处判据**（`available()`）：客人场景 / 非搭档一律没有工具。
  工具是能力，不能绕过"客人不写记忆"这条边界。对方搞了七层开关 + 一个审计脚本兜底，
  我们不挖这个坑。
- ✅ **参数错了把可用值喂回去**：写了不认识的人 → 回"你不认识叫「张三」的，
  你认得的是：椎名"，而不是"参数错误"。也**不允许 `forget` 忘掉她此刻看不见的记忆**。
- ✅ **工具协议写进系统提示词**。这条是实测踩出来的：只把 `tools` 传给 API、
  不在提示词里告诉她"你有这些能力"，她会把"我记住了"当台词说出来，**三轮里零调用**。
  对方提示词第 3 段就是"工具协议"——这不是可选项。

### 第 4 批：工程能力

- ✅ **LLM 当裁判的触发决策评测**（`tools/judge_cases.json` + `tools/judge_check.py`）：
  30 条用例（12 正 / 18 负）、准确率 + **混淆矩阵**、**误开口单列**，
  硬规则"误开口 > 0 就不建议自动开口"；没配 API key 时干净跳过（退出码 0）。
  裁判自身的稳定性照抄了对方的规矩：判不了算保守、出错一律判"不发"、解析要宽容。
- ✅ **静态一致性审计**（`tools/audit.py`）：配置项"声明↔读取"双向核对、
  指令"声明↔实现"双向核对、**发送路径不得绕过 `send()`**、脚本至少有一条断言。
- ✅ **运行档案** `data/runs.jsonl`：每次处理记一行（提示词多大、想起几条、说出口几条）。
  排障时回答"她当时到底看到了什么"，**不记对话内容**（数据库里已经有了）。
- ✅ **内部调用关思考**：我们的 DeepSeek 配置本来就是 `thinking=false`，
  所有调用（含整理/裁判类）都不烧推理预算。
- ✅ **死配置清理**：`unit_label`、`recall_candidates`、`greeting_line` 从没被读过，
  删掉；`reconcile_min_memories` 之前声明了却写死成 4，改成真的读配置。

## ✗ 明确不做（都有证据）

| 不做什么 | 为什么 |
|---|---|
| **插件能力注册表 + hooks + 热重载** | 那是给第三方生态付的税，我们没有第三方。**但判据值得记：「规则能写死 → 代码；要理解人话 → 交给模型」** |
| **字符串全等去重** | 改写/换名会堆积；我们的 `similarity` + 模型逐对确认更强 |
| **无检索、无衰减**的注入 | 别为省 token 退回"一股脑塞" |
| **硬编码截断**（300 字 / 120 字 / 15 人） | 长记忆静默丢内容 |
| **整目录重写** | 中断只剩备份；SQLite 事务更稳 |
| **规则堆砌** | 对方 13 个大段里"反AI味/主体性/不是客服队列"语义高度重叠，**它自己的注释承认"模型不把人设正文当行为指令"** |
| **靠词表去 AI 味** | 过拟合特定群语感；我们的置信度标记是**机制化**的 |
| **体量失控**（单文件 1245 行 / 编排 2045 行） | 零依赖的可读性优势被自己吃掉 |
| **常量写在注释里** | 无法执行。我们应该落成**断言** |
| **掷骰两次**（预判与实跑不一致）被文档化成"不是缺陷" | 应只算一次并落库（我们已在 `trigger.decide` 里写明） |
| **测试依赖不随仓库分发** | 对方的 `judge-check.mjs` import 了不在仓库里的文件，clone 后必挂。我们的自测必须自包含 |
| **拿提示词当安全边界** | 靠"最后 3 轮催一次"纠行为是补丁 |
| **桌面壳 / 自带 QQ 客户端** | 交付形态完全不同，且有合规风险 |
| **手抄农历表** | 对方抄错了（2027 重阳差一天）。要加农历必须离线算 + 交叉验证 |

## ★ 我们做得更好、要保持的

- **确定性断言**（461 项，自包含）——对方是 26 个脚本长链，还有的依赖不在仓库里
- **SQLite 事务**——对方一人一文件 + 删后重建
- **`similarity` + 模型逐对确认**的去重——对方是字符串全等
- **"新版本更长就让旧条目长大"**（记忆演进）——对方"只减不增"
- **BM25 + 保留率 + blur** 的检索式记忆——对方是固定注入。我们更贵，但"该想起什么"更准
- **记忆分区的隐私闸门**（scope/subject/about）——对方按会话+人隔离，没有"私事 vs 群公开"这一层
- **机制化的置信度标记**（可以确信/需要含糊/只是隐约）——对方靠词表
- **发送成功才记账**（主动联系）——这点对方也做对了
- **发送失败如实上报**（`9e1b104` 修的）——对方也做对了，我们原来做错了

## 平台事实（已核实，影响长期规划）

- **历史聊天记录两条路都得靠自己在线存**：官方 API **没有**拉取接口（v2 只有事件 + 发送）；
  OneBot 有扩展 `get_group_msg_history`，但对方自己也没用，历史全靠在线存档。
  所以"听到一条存一条"不是我们的妥协，是唯一可行方案。
- **全量群消息**：官方要群管理员在资料页开开关，**而且用户随时会关**（会推 `GROUP_MSG_RECEIVE/REJECT`）；
  OneBot 因为登录了客户端本来就看得见、关不掉 —— 所以"按概率插嘴"在官方路线上输入不稳定。
- **openid 与 QQ 号不互通**，认人只能靠"谁先说话"（自动认主）或 `/bind`。
