## 2. 更新网站与更新 APK 的区别

- 改 Python、人格或网页后，按网站流程部署；App 仍加载同一个域名，不需要为这些改动重新打 APK。
- service worker 可能先显示本地缓存的壳，再后台更新；部署后若仍看到旧界面，刷新或关闭后重新打开。
- 修改包名、启动域名、Android 壳本身或签名时，需要重新构建、签名并检查网站关联声明。
- 更新同一安装的 APK 应沿用原包名与签名，并使用新的版本号。替换成新密钥不能当作原安装的普通升级。

App 中仍使用搭档 / 访客口令，APK 不内置网页口令。浏览器与 App 是否共享 cookie / 显示历史
取决于实际运行环境；不要把服务端同一份记忆理解成所有设备都同步了聊天列表。

## 3. 后续重新打包的流程

这是维护流程，本次未执行。不能再把“下载 ZIP”当作“已得到可安装 APK”。

1. 检查线上 `manifest.json`、service worker 和 HTTPS，确认仍加载 `https://giftia.icu`。
2. 如继续使用 PWABuilder，以现有包名 `icu.giftia.twa` 为准，保留原应用身份。
   云端页面的字段可能改变，不依赖旧文档中的 “Create new signing key” 按钮是否存在。
3. 检查构建产物是否已签名。历史上下载的是 `-unsigned.apk`，直接安装出现过
   `packageInfo is null`；该问题随后通过本地签名解决。
4. 使用原 keystore 做对齐和签名。历史工具是 uber-apk-signer；仓库没有封装好的一键签名命令。
5. 用所用 Android 工具链的签名验证命令确认签名有效，检查包名、版本号和证书指纹。
6. 核对 `web/.well-known/assetlinks.json` 的 `package_name` 和 `sha256_cert_fingerprints`。
   正常沿用原证书时不需要更换指纹；有意更换证书时要同时规划已有安装的迁移。
7. 部署关联声明后检查线上返回，再在设备验证安装、无地址栏打开、登录、聊天和通知：

   ```bash
   curl https://giftia.icu/.well-known/assetlinks.json
   ```

签名密钥、密码和下载产物单独备份，不写入文档或仓库。

## 4. 通知和离线能力

Web Push 只面向搭档；访客不能订阅或读取主动消息。
它依赖浏览器 / 系统推送能力、通知权限、服务端 VAPID 和网络，不是独立实现的原生安卓推送 SDK。

当前前端按服务端“是否存在任何订阅”决定隐藏订阅按钮，所以换设备后可能不显示按钮，
即使这台设备尚未订阅；这是现存实现限制，见 [WEB.md](WEB.md)。
推送只补最近一条主动消息，完整聊天列表仍保存在设备 localStorage。

离线缓存只覆盖静态页面壳。离线时可以打开缓存界面，不能调用云端模型继续聊天。

## 5. PWA 与其他平台

不安装 APK 时，可在支持的手机浏览器中把网站添加到主屏幕。
本仓库提供 PWA 清单和静态壳，没有 iOS 原生工程或 IPA 构建流程。
能否安装到主屏幕、全屏运行和接收通知，以具体浏览器与设备能力为准。

## 6. 排障

| 现象 | 核对项 |
|---|---|
| 安装失败 / `packageInfo is null` | 是否误用了未签名产物；先查签名验证结果，再查设备安装错误 |
| App 顶部出现地址栏 | 线上 assetlinks 的域名、包名和签名指纹是否与安装包匹配 |
| 网站更新了，App 仍旧 | 静态文件是否已部署、service worker 是否已刷新缓存 |
| 她显得更客气 | 是否使用了访客口令；搭档与访客不是同一视角 |
| 没收到主动通知 | 搭档登录、通知权限、本机订阅、`sent / total` 和推送中转日志 |
| 换手机后没有过去的聊天列表 | 当前没有跨设备历史拉取，服务端记忆仍是同一份 |
