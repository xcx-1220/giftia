## 怎样避免再次混乱

1. **计划只有一份。** 新需求先加入路线图并分配 ID，不再新建平行的 `PLAN`、`BACKLOG` 或“总方案”。专项细节可放记录文件，但状态、优先级和完成判据仍在路线图。
2. **说明、计划、结果分开。** 当前文档描述已经存在的行为；路线图写将要做的事；`records/YYYY-MM-DD-主题.md` 写实际做了什么、结果、限制与关联任务 ID。
3. **区分状态。** 使用「已部署」「本地候选」「待验证」「待开始」「后置」「暂不做」。本地代码、机制测试、模型体验、设备交付分别验收，不能相互替代。
4. **事实带日期和范围。** 测试数只写在相应记录；当前文档链接该记录。部署记录写源码版本、有效配置摘要和核对范围，不能只写“最新版”。
5. **先保留证据，再归档。** 完成项在路线图留简短结论与记录链接；过期大方案移入归档并注明替代入口，不删除失败样本。
6. **代码与线上分开。** Markdown 不会自动注入角色。实际提示来自配置与代码；线上状态由部署核对确认，不能由本地 HEAD 推断。
7. **引用使用相对路径。** 移动文件同时修正仓库内 Markdown 链接。归档内反引号包裹的代码路径、行号和命令保留当时语境，通常以仓库根目录为基准。
8. **文档不存秘密。** 凭据、私钥、完整私人聊天和可直接使用的认证信息不进入文档。配置只写键名；敏感原始样本放受限位置。

这次归档保留历史正文，添加状态提示并修正可解析的本地 Markdown 链接。旧计划中的“下一步”“已完成”属于当时记录；执行时以当前路线图与最新核对结果为准。
